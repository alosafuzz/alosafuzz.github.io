## 1. What it is & where it runs

**IEEE C37.118** is the synchrophasor protocol: it carries time-stamped voltage and current phasor
measurements from **PMUs** (phasor measurement units, out in substations) to **PDCs** (phasor data
concentrators) and up into **WAMS** (wide-area measurement systems) that operators use to watch grid
stability in real time. C37.118.2 is the data-transport half of the standard (C37.118.1 is the
measurement half). It is the dominant protocol for wide-area grid visibility in North America and
widely deployed elsewhere.

For a researcher the important facts are the trust model and the data flow. A PMU streams frames to a
PDC over TCP or UDP (commonly port 4712/4713); the PDC parses every frame it receives and aggregates
them. C37.118 has **no authentication or integrity of its own**; the security story is whatever the
surrounding network provides (a VPN, a serial link, or nothing). So the realistic attacker is a rogue
or spoofed PMU, or a man-in-the-middle on the PMU-to-PDC path, and the thing under attack is the
**PDC's frame parser**, which runs on bytes from the field before any application logic.

## 2. The frame model

Every C37.118 frame shares a common header:

- **SYNC** (2 bytes): a leading `0xAA` plus a type field (data, header, config-1, config-2,
  config-3, command) and a version.
- **FRAMESIZE** (2 bytes): the total frame length.
- **IDCODE** (2 bytes): the stream/PDC id.
- **SOC** (4 bytes) + **FRACSEC** (4 bytes): the timestamp.
- Then a type-specific body, and a trailing **CHK** (CRC-CCITT).

The four bodies a receiver parses:

- **Configuration frame** (CFG-1/2/3): the schema. It declares `NUM_PMU`, and for each PMU station a
  16-byte name, a format word, and the counts `PHNMR` / `ANNMR` / `DGNMR` (number of phasor, analog,
  and digital channels), followed by per-channel names and conversion factors. This is the richest
  variable-length structure, and the counts here drive how later frames are parsed.
- **Data frame**: the measurements. It is parsed **against the counts from the config**: for each
  PMU it reads STAT, then `PHNMR` phasors, `ANNMR` analogs, `DGNMR` digitals.
- **Header frame**: free-form ASCII.
- **Command frame**: a 2-byte command from the PDC to the PMU (send config, turn data on/off).

The researcher's hooks are the classic length-and-count surfaces: does `FRAMESIZE` get validated
against the bytes actually received? Do the per-station counts (`NUM_PMU`, `PHNMR`, `ANNMR`, `DGNMR`)
get checked against the remaining frame before the parser loops on them? A config that declares more
channels than the frame carries, or a data frame shorter than the config implies, is the core of the
attack surface.

## 3. The fuzz surface, mapped to Open-C37.118

[Open-C37.118](https://github.com/marsolla/Open-C37.118) (GPL-3.0, C++) is the open reference C/C++
implementation; vendor products fork it. The receiver parsers are the seam:

- **`CONFIG_Frame::unpack(unsigned char *buffer)`** (`src/c37118configuration.cpp`), the
  self-contained, highest-value target. It reads `pmu_count`, then per station a 16-byte name and the
  `PHNMR`/`ANNMR`/`DGNMR` counts, then walks two cursors through the per-channel names and conversion
  factors. A PDC calls it directly on the socket buffer (`examples/pdc.c`:
  `read(sock, buffer_rx) -> my_config2->unpack(buffer_rx)`).
- **`DATA_Frame::unpack`** (`src/c37118data.cpp`), parsed against a previously received config, so
  its reads are driven by that config's counts.
- **`COMMAND_Frame::unpack` / `HEADER_Frame::unpack`**: same shape, smaller.

The signature is the tell: `unpack()` takes a buffer and **no length**. A faithful harness feeds the
bytes a `read()` would deliver, and (following the standard practice for finding over-reads) uses
a tight `malloc(size)` buffer so a read past the frame is caught immediately rather than hidden in
the 80000-byte receive buffer the reference uses.

## 4. Known bug classes

C37.118 has a history of parser bugs, but in **other** codebases, which makes them the right prior
for the protocol rather than this library:

- **[CVE-2023-0668](https://takeonme.org/cves/cve-2023-0668)**: a heap-based buffer overflow in
  **Wireshark's** C37.118 dissector (a crafted packet, out-of-bounds read, possible code execution),
  fixed in 4.0.6.
- **[CVE-2026-95395](https://www.wireshark.org/security/wnpa-sec-2026-96.html)**: a memory leak in
  Wireshark's C37.118 dissector.
- **CVE-2013-2800 / CVE-2013-2801**: memory corruption / exhaustion when **OSIsoft's** PI Interface
  for C37.118 processes configuration packets.
- The **[PhasorSec](https://www.iti.illinois.edu/credc/publications/phasorsec-protocol-security-filters-wide-area-measurement-systems)**
  work (Dartmouth/Illinois) built a *hardened* C37.118 parser with parser combinators precisely
  because, in their words, the verbose spec makes a hand-written parser error-prone.

So the question for any C37.118 receiver is the same: are `FRAMESIZE` and the per-station counts
validated against the received length before the parser trusts them?

## 5. Research status and disclosure

I fuzzed the Open-C37.118 configuration parser in-process under AddressSanitizer, UndefinedBehavior-
Sanitizer, and MemorySanitizer, and found a memory-safety issue consistent with the class above.
**It was reported under coordinated disclosure; the fix is merged upstream and the advisory is
published ([GHSA-h97w-jg62-9qhg](https://github.com/marsolla/Open-C37.118/security/advisories/GHSA-h97w-jg62-9qhg)).** The companion writeup has the methodology and the
per-finding detail. Nothing here is a proof of concept.

## 6. Defensive notes

- **Keep the PMU-to-PDC network isolated.** C37.118 authenticates nothing; the parser runs on
  whatever reaches the port. Segment the WAMS network, and prefer an authenticated transport (the
  newer IEC 61850-90-5 routable profile, or a VPN) over raw C37.118 on a shared network.
- **Validate at the concentrator.** A PDC ingesting many PMU streams is the aggregation point and the
  highest-value target; if you integrate a C37.118 stack, audit its frame parser for `FRAMESIZE` and
  count validation against the received length.
- **Treat the configuration frame as the control input.** The counts a config declares drive how
  every later data frame is parsed, so a malicious config is a lever over the whole stream.
